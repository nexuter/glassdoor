01모든 설계를 좌우한 발견

스키마 작업에 앞서 반드시 확인해야 할 구조적 질문이 하나 있었습니다. 월별 디렉터리는 증분(delta)인가, 전체 덤프인가?

가정이 아니라 실측

모든 월별 디렉터리는 누적 전체 재덤프입니다. 2022-06과 2022-07 빈티지 전체를 레코드 단위로 비교한 결과는 다음과 같습니다.

어떤 레코드도 사라지지 않으며, 페이로드는 사실상 정적입니다. 기업은 한 달에 1,000건 중 약 4건, 리뷰는 1,000건 중 1건 남짓만 바뀝니다. 47개 스냅샷을 있는 그대로 저장하면 기업 약 5,600만 행, 리뷰 약 14억 행이 되는데 그중 99% 이상이 이미 존재하는 행의 완전한 중복입니다.

변경 감지에 숨어 있는 함정

doc만이 아니라 레코드 전체를 해시하면 리뷰의 월간 변경률이 11.7%로 나옵니다. 이는 재수집 때마다 갱신되는 _meta.updated_at_timestamp 때문이지 내용이 바뀐 것이 아닙니다. 버전 관리는 레코드가 아니라 페이로드 기준이어야 합니다.

따라서 설계 원칙은 한 번만 적재하고 변경분만 버전으로 남긴다입니다. 행 해시를 키로 한 Type-2 SCD를 적용하면 기업은 약 190만 기준 행에 수백만 변경 행, 리뷰는 실제 존재하는 약 4,200만 건으로 줄어듭니다. "2024-03 시점의 패널"은 여전히 조회할 수 있으며, 저장된 사본이 아니라 범위 조건이 됩니다.

02디스크 위에 실제로 있는 것

두 개의 병렬 트리, 빈티지마다 하나의 디렉터리, 세 단계 아래에 gzip JSON 샤드. 그리고 빈티지마다 겉보기보다 훨씬 유용한 부속 파일 네 개가 함께 들어 있습니다.

glassdoor/
  Glassdoor Data Dictionaries.pdf     # Coresignal 문서: 기업 7p + 리뷰 4p
  companies/YYYYMM/<3-hex>/<md5>.json.gz
  reviews/YYYYMM/<3-hex>/<md5>.json.gz
  reviews/companies/202601/           # companies/202601의 중복 — 제거 완료
  *.zip                               # 원본 아카이브 약 288 GB, 검증 후 삭제 가능

부속 파일

파일용도
ids_*.txt해당 빈티지의 전체 레코드 id 목록. 정확한 행 수를 공짜로 얻을 수 있고, ETL의 적재 완결성 검증 기준이 됩니다.
glassdoor_*_latest.json레코드의 JSON Schema. 낡았습니다. 리뷰 쪽 스키마에는 language, author_status, advice_to_management가 빠져 있습니다. 이 파일이 아니라 데이터를 신뢰해야 합니다.
CHANGELOG.*.yamlCoresignal이 직접 작성한 필드 변경 이력. 마지막 항목이 2022-03이라 §04에서 관찰된 변동은 전혀 담고 있지 않습니다.
DISCLAIMER.txt라이선스 조항. 아래 상자를 참고하십시오.
라이선스가 배포 방식을 결정합니다

모든 빈티지에는 데이터가 저작권과 영업비밀의 보호를 받으며, 데이터베이스 구조도 데이터 자체도 공개하거나 재배포할 수 없다는 고지가 붙어 있습니다. 따라서 웹 인터페이스는 처음부터 인증과 접근 기록을 갖추어야 합니다. 마지막에 덧붙일 장식이 아니라 전제 조건입니다.

샤드 형식

모든 .json.gz는 정확히 10,000건을 담고 있으며, JSON 배열을 예쁘게 출력한 형태로 한 줄에 레코드 하나씩(앞에 탭, 끝에 쉼표) 들어 있습니다. 덕분에 로더는 줄 단위로 스트리밍할 수 있어 증분 JSON 파서가 필요 없고, 샤드는 그대로 병렬 처리됩니다. 이 장비에서 단일 스레드 실측 처리량은 gunzip·id 추출·해싱을 모두 포함해 초당 약 43,500건이었습니다. 47개 빈티지 전체를 한 번 훑는 데 순차로 약 9시간, 워커 8개로는 약 1.5시간입니다.

함정이 하나 있습니다. 디렉터리 버킷은 파일명의 앞 세 자리 16진수이고, 파일명은 md5(첫 레코드의 doc.id)입니다. 내용 해시 버킷이 아닙니다. 청크 경계와 파일명이 빈티지마다 달라지므로 두 달치를 파일명으로 비교할 수 없습니다.

03시점에 따른 수록 범위

증가는 자연스럽지 않고 계단식입니다. Coresignal이 수록 범위를 여러 차례 넓혔고, 그 계단은 기업의 시장 진입이 아니라 수집 이벤트입니다. 그대로 두면 패널이 이를 진입으로 읽습니다.

기업 (왼쪽 축) 리뷰 (오른쪽 축)

계단의 폭이 큽니다. 기업은 2023-07에 +13.4만, 2023-11에 +23.1만, 2025-03에 +13.0만, 2025-10에 +38.3만이 늘었고, 리뷰는 2023-06에 +540만, 2026-03에 +324만이 늘었습니다. 어떤 기업이 처음 등장한 시점을 진입 사건으로 해석하거나 리뷰 급증을 게시량 증가로 해석하면, 실제로는 이 수집 이벤트를 집는 셈이 됩니다. 패널에는 first_vintage 열이 명시적으로 필요하고, 코드북에는 이 날짜들이 기록되어야 합니다.

04스키마 변동

기업 8개, 리뷰 8개의 추출 스키마가 존재합니다. 과거 레코드는 소급 갱신되지 않기 때문에 2026년 빈티지 안에도 2021년 스키마로 만들어진 레코드가 남아 있고, 두 가지 명명 규칙이 한 파일 안에 나란히 존재합니다.

패널 작업에 미치는 영향

2023년 이후에 추가된 변수는 과거 빈티지에서는 물론이고 최신 빈티지 안의 오래된 레코드에서도 구조적으로 결측입니다. 정규화 로직은 빈티지가 아니라 version_id를 기준으로 분기해야 합니다. 코드북에는 변수별 first_available 열이 필요하고, 추출 기능은 내려받는 파일마다 수록 범위 안내를 함께 붙여야 합니다.

05데이터 품질

문서가 아니라 데이터에서 직접 확인한 이슈 15건입니다. 이 중 셋은 놓치면 결과를 조용히 오염시킵니다.

06데이터베이스 설계

PostgreSQL을 원본 시스템으로 두고, 대량 추출용 고속 경로로 Parquet 사본을 둡니다.

Postgres는 동시 사용자, 인증, 행 수준 접근 제어, 감사 로그를 제공하며 리뷰 본문 전문 검색도 tsvector에 GIN 인덱스를 걸면 충분히 감당합니다. 같은 테이블을 파티션된 Parquet으로 복사해 DuckDB로 읽으면 대용량 CSV 추출이 빨라지고, 오프라인 분석 경로도 열립니다. 예상 용량은 Postgres 약 100 GB(이 중 본문과 인덱스를 포함한 리뷰가 60~80 GB), Parquet+zstd 약 35 GB입니다.

전체 본문 스캔만 놓고 보면 ClickHouse가 둘보다 빠르지만, 소규모 연구 그룹이 감당할 만한 운영 부담은 아닙니다. 전문 검색이 실제로 느리다고 판명될 때만 다시 검토하면 됩니다.

핵심 테이블

중요한 인덱스

  • review (company_sk, review_date) — 압도적으로 가장 많이 쓰이는 접근 경로
  • 각 파티션 내부의 review (review_date)
  • review (star_overall), (language), (author_status) — 선택도가 높은 필터
  • review_text.search_tsv의 GIN 인덱스 — 장점·단점·요약·경영진 조언 통합 키워드 검색
  • 자동완성을 위한 company.name trigram 인덱스와 company_version의 SCD 구간 인덱스

07웹 인터페이스

기준은 하나입니다. SQL을 한 번도 써본 적 없는 사람이 표본을 정의하고 변수를 고른 뒤 CSV를 받아 갈 수 있어야 합니다. 화면 다섯 개면 됩니다.

01기업 찾기

이름 자동완성과 함께 산업, 국가, 규모 구간, 매출 구간, 설립 연도, 평점 범위로 필터링합니다. 필터를 건너뛰고 Glassdoor 기업 id 목록을 붙여넣거나 업로드해 표본을 바로 정의할 수도 있습니다.

02리뷰 질의 작성

표본 × 기간 × 필터(종합·세부 평점, 추천 여부, CEO 지지, 사업 전망, 재직 형태, 현직/전직, 근속, 언어, 본문 유무)에 더해 장점·단점·요약·경영진 조언 안의 키워드 검색까지 조합합니다. 변수는 분류별 체크박스 목록에서 고르고, 확정 전에 예상 행 수를 실시간으로 확인합니다.

03기업 패널 작성

원본 Glassdoor에서는 얻을 수 없는 기능입니다. 기업, 기간, 주기, 변수를 고르면 버전 이력에서 균형 잡힌 월별 패널을 구성해 줍니다. §03과 §04의 수록 범위 단절 및 최초 제공 시점 경고가 결과물에 함께 붙습니다.

04다운로드 센터

규모가 조금이라도 있는 요청은 모두 백그라운드 작업으로 처리합니다. WRDS와 같은 방식입니다. CSV, TSV, Parquet, Stata 형식을 gzip으로 압축해 만료되는 링크로 제공하고, 결과를 재현하고 인용할 수 있도록 질의 조건을 결과물과 함께 저장합니다.

05코드북

스키마와 §05의 프로파일링 통계에서 자동 생성합니다. 변수마다 자료형, 결측률, 센티널 처리 방식, 그리고 애초에 어느 빈티지부터 존재하는지를 보여줍니다.

여기에 더해, 별도 DB 역할과 구문 제한 시간·행 수 상한을 건 읽기 전용 SQL 콘솔을 상급 사용자에게 제공합니다. 로그인과 약관 동의는 필수이며, 다운로드 감사 로그는 라이선스상 사실상 요구 사항입니다.

스택은 FastAPI와 SQLAlchemy에 JSON→SQL 질의 변환 계층, 추출 작업용 arq 또는 Celery 워커, 그리고 서버 렌더링 HTMX 프런트엔드를 제안합니다. 빠르게 만들 수 있고 유지할 SPA가 없습니다. React 프런트엔드가 꼭 필요하다면 물론 바꿀 수 있습니다.

08단계별 계획

엔지니어 한 명 기준으로 사내에서 쓸 수 있는 서비스까지 대략 8~11주입니다. 각 단계는 앞 단계에 실제로 의존하므로 순서를 지켜야 합니다.

P0결정과 환경 준비§09를 확정하고 Postgres와 오브젝트 스토리지를 준비하며 저장소를 정리합니다.1~2일

09P1 착수 전에 필요한 결정

이 검토를 시작할 때 여섯 가지였고, 그중 하나는 실측으로 해결되었습니다. 나머지는 설계보다 운영 방식에 더 크게 영향을 줍니다.

  1. 리뷰는 전체 이력인가, 최신 상태만인가? 해결 — 이력을 남깁니다

    리뷰 페이로드 변경률은 월 0.12%로, 2022-06과 2022-07 사이에 20,367행이 바뀌었습니다. review_version 테이블은 47개 빈티지 전체에서 100만 행 안팎이면 충분하므로 부담이 없습니다. 만드는 쪽이 맞습니다.

  2. Postgres인가, DuckDB만인가?

    동시 사용자가 몇 명입니까? 실제로 연구자 1~3명 규모라면 Parquet 위의 DuckDB에 얇은 프런트엔드를 얹는 구성으로 구축 비용이 대략 절반이 됩니다.

  3. 어디에서 운영합니까?

    여유 공간이 5.5 TB인 이 D: 볼륨의 로컬 서버입니까, 기관 서버나 클라우드입니까? 이 선택이 인증 방식을 결정합니다.

  4. 누가 로그인할 수 있습니까?

    Coresignal 약관을 보면 라이선스를 보유한 기관 내부의 기명 계정으로 한정하는 것이 자연스럽습니다. P6이 끝난 뒤가 아니라 그 전에 확인해 두는 편이 좋습니다.

  5. 추출 상한은 어떻게 둡니까?

    다운로드 1건당 행 수 상한, 보관 기간, 그리고 리뷰 원문을 대량으로 내보낼 수 있는지 아니면 집계만 허용할지를 정해야 합니다.

  6. .zip 아카이브는 삭제합니까?

    추출된 트리를 바이트 단위로 검증한 뒤 삭제하면 약 288 GB를 회수할 수 있습니다.
